S3 stores objects (bytes + metadata) in **buckets** addressed by key over an HTTP API. It offers
practically unlimited capacity, very high durability, and low cost. It is the default home for media,
backups, logs, data lakes and static websites.

## Model

- **Bucket** (globally unique name) → **objects** identified by **key** (a flat namespace; slashes are just characters, "folders" are a UI convention).
- Object = data (up to 5 TB) + system/user metadata + tags + version ID.
- API: `PUT`, `GET` (with range reads), `DELETE`, `LIST` (prefix + delimiter), `HEAD`, multipart upload, presigned URLs.
- **Strong read-after-write consistency** for new objects, overwrites, deletes and list operations.
- Objects are **immutable**: an update replaces the whole object (no partial writes).

## Durability and availability

- Designed for **11 nines (99.999999999%)** durability by storing data redundantly across at least three Availability Zones, with checksums verified and repaired continuously.
- Availability differs by storage class (e.g. Standard 99.99%).
- **Versioning** protects against accidental deletes/overwrites; **Object Lock** (WORM) for compliance; **cross-region replication** for DR and locality.

## Storage classes and lifecycle

| Class | Access pattern | Notes |
|---|---|---|
| Standard | Frequent | Default, lowest latency |
| Intelligent-Tiering | Unknown/changing | Automatic tiering |
| Standard-IA / One Zone-IA | Infrequent | Cheaper storage, retrieval fee |
| Glacier tiers | Archive | Minutes to hours to retrieve, cheapest |

**Lifecycle rules** transition or expire objects by age/prefix/tag; essential for cost control in
media, logs and backups.

## Upload and download patterns

- **Presigned URLs**: your API authenticates the user and returns a time-limited URL; the client uploads/downloads **directly** to S3, keeping bytes off your servers.
- **Multipart upload**: split large files (parts 5 MB–5 GB, up to 10,000 parts) uploaded in parallel with independent retries, then completed; also enables resume.
- **Range GET** for seeking (video segments, parquet column reads) and parallel downloads.
- **Transfer acceleration** and CDN (CloudFront) for global clients and hot content.
- **Event notifications** (to SQS/SNS/Lambda/EventBridge) trigger processing: thumbnails, transcoding, virus scan, indexing. See [Uploading and Serving Large Files](../05-Interview-Patterns/07-uploading-and-serving-large-files.md).

## Performance and scale

- Scales to thousands of requests per second **per prefix** (3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD per second per prefix); spread keys across prefixes for higher aggregate throughput.
- High latency per request (tens of ms) compared to a database: batch/parallelise, cache metadata elsewhere.
- Small objects are inefficient (per-request cost and latency); bundle them (tar/parquet) for analytics.

## Security

Private by default; bucket policies, IAM, ACLs, block-public-access, server-side encryption (SSE-S3, SSE-KMS), client-side encryption, VPC endpoints, access logging, signed URLs.

## How S3 works internally (conceptual)

A front-end fleet authenticates and routes requests; an index/metadata layer maps `(bucket,key)` to
data locations (a large partitioned, replicated key-value store); data is stored as erasure-coded or
replicated shards across zones; background scrubbers verify checksums and repair. See
[Design Object Storage like S3](../15-Distributed-Infrastructure/Object-Storage-S3/README.md).

## Common architectures

| Use | Design |
|---|---|
| Image/video platform | Upload via presigned multipart → S3 → event → workers → renditions in S3 → CDN; metadata in a DB |
| File sync/drive | Chunk hashes, content-addressed blocks in S3-like store |
| Data lake | Parquet/ORC in S3, query with Athena/Spark/Presto |
| Backups/archive | Lifecycle to Glacier |
| Static site | S3 + CDN |

## Limits and gotchas

- No append or in-place edit; renaming = copy + delete.
- `LIST` is paginated and relatively slow/expensive; keep an index in a database for queries.
- Egress and request costs matter at scale.
- Not a filesystem: no POSIX locking or atomic multi-object operations.

## Interview questions (with answers)

**Q1. How do you let a browser upload a 5 GB file reliably?** API issues presigned multipart-upload URLs; browser uploads parts in parallel with per-part retry; complete-upload call; server verifies and marks the file ready.

**Q2. Why store metadata in a database rather than S3?** S3 is optimised for blobs by key; listing/querying by attributes is slow and limited. A DB holds searchable metadata with a pointer (`bucket/key`).

**Q3. How do you delete a user's data (GDPR)?** Delete objects and versions (with lifecycle/expiry), purge derived copies (CDN, backups by schedule), and log the deletion.

**Q4. How do you reduce storage cost?** Lifecycle to cheaper tiers, delete unused renditions, compress, dedupe by content hash, intelligent tiering.

**Q5. How does S3 achieve high durability?** Redundancy across AZs (replication or erasure coding), end-to-end checksums, continuous scrubbing and automatic repair.

## Last-minute revision

Flat key → blob; immutable; 11 nines; presigned + multipart for big files; events to trigger pipelines;
lifecycle for cost; metadata in a DB; CDN in front for reads.
